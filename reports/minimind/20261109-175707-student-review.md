# 수강생 관점의 LLM·MiniMind 학습 자료 검토

검토 ID: 20261109-175707-student-review.

## 판단

**기본 구조와 학습 순서를 따라가는 실습으로는 사용할 수 있다. 그러나 현재 노트북만으로 처음 배우는 수강생이 학습 원리를 스스로 설명하고 원본 MiniMind trainer를 독립적으로 읽을 수 있다고 보기는 어렵다.** PyTorch의 `nn.Module`, autograd, optimizer, cross entropy를 이미 아는 수강생이라면 이해할 수 있는 범위가 넓어진다. README가 권장하는 강사의 설명이 함께 있는 수업과 독학 상황을 구분해야 한다.

이번 검토는 Python 기본 문법·텐서 인덱싱을 알고 LLM은 처음 접하는 학습자를 가정한 순차 독해 검토다. 실제 인간 수강생의 이해도 측정 실험은 아니다. 모든 기본 셀을 다시 실행한 검토도 아니다. 설명·실행 코드·과제·원본 함수 연결을 읽고, 실제로 막힐 가능성이 높은 3장의 설정 변경 과제만 별도로 재현했다. 노트북과 모델 소스는 수정하지 않았다.

## 먼저 해결할 학습 장애

### 1. 안내된 GQA 과제를 설정 변경만으로 수행하면 오류가 난다 — 우선순위 높음, 실행 재현

대상: [3장 Attention](../../notebooks/Chapter_3_Exercise_MiniMind_Attention.ipynb), JSON cells 인덱스 **6**의 GQA 수동 계산과 인덱스 **11**의 제출 과제. 셀 번호는 0부터 시작한다.

과제는 `num_key_value_heads`를 1·2·4로 바꿔 파라미터 수를 비교하라고 한다. 하지만 수동 계산은 다음 값을 고정한다.

```python
q = attn.q_norm(attn.q_proj(h).view(1, 6, 4, 16))
k = attn.k_norm(attn.k_proj(h).view(1, 6, 2, 16))
v = attn.v_proj(h).view(1, 6, 2, 16)
k_heads = repeat_kv(kr, 2).transpose(1, 2)
```

| KV heads | 노트북 수동 계산 셀 | 실제 MiniMind Attention 모듈 |
|---:|---|---|
| 2 | 통과 | 출력 `[1,6,64]` |
| 1 | `shape '[1, 6, 2, 16]' is invalid for input of size 96` | 출력 `[1,6,64]` |
| 4 | `shape '[1, 6, 2, 16]' is invalid for input of size 384` | 출력 `[1,6,64]` |

모델의 GQA 구현 문제가 아니라 **노트북 실습 셀의 고정 shape 문제**다. 수강생은 올바른 설정을 바꾸고도 자신의 원리 이해가 틀린 것처럼 받아들일 수 있다. batch·sequence 길이·Q/KV head 수·head_dim·반복 횟수를 실제 입력/config에서 계산하도록 바꾸고, 설정을 바꿀 때 어느 셀부터 다시 실행하는지도 안내해야 한다. helper는 4/2 head 설정을 내부에서 만들므로 설정을 바꿀 별도 셀도 필요하다.

재현 데이터: [gqa-exercise-check.json](../../outputs/minimind/20261109-175707-student-review/gqa-exercise-check.json). 이 결과는 기본값 2의 실행 통과와 모순되지 않는다. 이전의 전체 기본 실행은 이 설정 변경 과제를 실행하지 않았다.

### 2. logits → 확률 → loss → gradient → 업데이트의 설명 연결이 짧다 — 우선순위 높음

근거:

- [1장](../../notebooks/Chapter_1_Exercise_MiniMind_Vector_Space.ipynb) 셀 8은 `F.mse_loss`, `backward`, `optimizer.step`을 사용하여 임베딩 행이 바뀌는 것을 보여 준다. 하지만 gradient와 학습률이 왜 그 방향으로 가중치를 바꾸는지 기초 설명은 충분하지 않다.
- [4장](../../notebooks/Chapter_4_Exercise_MiniMind_Architecture.ipynb) 셀 4는 `[B,T,V]` logits와 수동 `F.cross_entropy`가 모델 loss와 같은지를 확인한다. 정답 확률을 높이는 목표와 cross entropy의 관계를 숫자로 풀지는 않는다.
- 3장의 softmax는 토큰 위치 간 Attention 확률이고, LM head 뒤의 vocabulary 확률과는 축과 의미가 다르다. 초보자가 두 종류의 확률을 구분할 명시적인 비교가 부족하다.

수강생 질문: **“행렬 계산이 맞는 것은 확인했는데, 마지막 숫자에서 정답 확률이 어떻게 나오고 loss가 줄면 왜 모델이 배운 것인가?”**

권장 보강: 3개 단어 vocabulary와 정답 1개를 두고 logits → softmax → 정답 확률 → `-log(p)`를 손으로 계산한다. 이어 한 번의 SGD 전후 정답 확률과 gradient를 출력한다. Attention softmax의 `[T,T]`와 LM softmax의 `[T,V]`를 나란히 표시한다. 그 뒤 `cross_entropy`가 이 과정을 내부적으로 수행함을 연결한다.

### 3. 원본 trainer로 넘어가는 실행 순서 안내가 부족하다 — 우선순위 높음

[5장](../../notebooks/Chapter_5_Exercise_MiniMind_Pretraining.ipynb)의 노트북 루프는 읽기 쉽고 forward/backward/clip/update 순서를 실제로 보여 준다. 하지만 [원본 train_pretrain.py](../../minimind/trainer/train_pretrain.py)를 열면 다음 단계를 별도로 알아야 한다.

```text
parse_args
→ 분산 모드·seed
→ config·재개 파일 확인
→ autocast·로깅
→ init_model·dataset·optimizer·scaler
→ 재개 상태 로딩
→ compile/DDP 래핑
→ epoch seed·sampler·SkipBatchSampler·DataLoader
→ train_epoch
→ 저장·정리
```

`train_epoch`는 `model`, `args`, `optimizer`, `scaler`, `autocast_ctx`, `lm_config` 등을 함수 인자가 아닌 외부 변수로 읽는다. 수강생은 “함수 인자에 없는 optimizer와 model은 어디에서 왔는가?”에서 막힐 수 있다. 노트북 helper의 `load_checkpoint`·`save_checkpoint`는 원본 `init_model`·`lm_checkpoint`와 형식·역할도 다르다. README는 차이를 경고하지만 코드 줄을 따라가는 연습까지 제공하지는 않는다.

권장 보강: 5장 끝에 **원본 trainer 읽기** 절을 두어 위 실행 순서를 표시하고, 실제 함수·변수의 생성 위치를 찾아 연결하는 과제를 넣는다. DDP/AMP 전체를 실행할 필요는 없다. 기본 CPU 단일 프로세스에서 지나가는 경로와 이번에 건너뛰는 경로를 구분하면 된다. 7·8장도 같은 지도에서 dataset과 trainable parameter 선택만 바뀌는 부분을 찾게 한다.

### 4. helper에 가려진 생성·데이터 처리와 설정의 위치가 보이지 않는다 — 우선순위 중간

매 장 setup 셀은 `from minimind_lab import *`와 `setup(...)`으로 시작한다. 편리하지만 초보자는 `MiniMindConfig`, `SFTDataset`, `loader`, `evaluate`가 원본 구현인지 수업 helper인지 쉽게 구별하지 못한다.

[2장](../../notebooks/Chapter_2_Exercise_MiniMind_Dataset.ipynb)은 `pretrain_data()`와 `sft_data()`로 올바른 실제 데이터셋을 사용한다. 그러나 학생이 JSONL 한 줄부터 `__getitem__`·collation·batch·labels·모델 loss까지 **어느 함수를 지나왔는지** 추적하는 작업은 남아 있다. 4장의 설정 변경 과제도 실제 기본 config가 helper 내부에 있어 수정 위치를 먼저 찾아야 한다.

권장 보강: 각 장 시작에 '이번 장에서 원본에서 가져오는 클래스 / 수업 편의 함수'를 짧게 구분한다. 모델 설정은 노트북에서 보이는 config 셀로 노출한다. 2장에 JSONL 한 줄 → Dataset[0] → DataLoader batch → forward(labels)의 추적 표를 넣고 실제 원본 함수명과 연결한다.

### 5. 개념이 필요한 순서와 설명 순서가 일부 맞지 않는다 — 우선순위 중간

- 1장의 과제는 문맥에 따른 hidden state를 설명하게 하지만 문맥화된 상태를 직접 보는 것은 뒤 장이다. token ID는 문맥 의미에 따라 바뀌는 값이 아니라 tokenizer의 표기·분할에 따른 값임을 함께 명시하는 것이 좋다.
- 3장에서 Q/K RMSNorm과 RoPE를 먼저 쓰고, RMSNorm 수식은 4장에서 설명한다. RoPE는 norm 보존 검사를 하지만 왜 위치 회전이 순서·상대 위치 정보를 주는지에 대한 기초 설명은 짧다.
- 4장의 순서는 기본 구조 → KV cache → 생성 API → norm/FFN → MoE → residual block 직접 연결 → 직접 생성 루프다. 초보자에게는 block 연산과 직접 생성이 cache/MoE보다 앞에 오는 편이 자연스럽다.
- 5장은 gradient accumulation·AMP·optimizer 재개를 먼저 다루고 실제 작은 언어 모델 학습 루프는 뒤에 나온다. 기초 autograd가 약한 수강생은 첫 학습을 보기 전에 운영 기능에서 길을 잃을 수 있다.

권장 순서: 작은 숫자의 loss/SGD → 단일 head → MHA → norm/FFN/residual → 전체 LM과 직접 생성 → 간단한 학습 → 원본 MiniMind의 GQA/RoPE·cache·실제 trainer 읽기. 기존 장 번호를 전면 변경하기보다 먼저 필요한 설명을 넣고 cache/MoE·AMP/누적/재개를 확장 절로 이동해도 된다. “선택”인 MoE는 현재 Run All에서는 실행되므로 읽기 경로에서 기본/심화 구분을 분명히 해야 한다.

### 6. 실행 성공과 학습자의 설명 능력을 구분할 확인 문제가 필요하다 — 우선순위 중간

assert와 수치 일치 검사는 구현의 신뢰성을 높인다. 하지만 완성 코드가 이미 제공되어 있어 전부 실행했다고 학생이 새 코드를 읽거나 오류 원인을 설명할 수 있는 것은 아니다. 결과 예측·직접 바꾸기 과제는 있지만 모범 reasoning이나 해설을 확인할 장치가 적다.

각 핵심 절에 다음 세 가지를 권장한다.

1. 실행 전 출력 shape·학습 대상·변하는 파라미터를 적는 작은 빈칸.
2. 실행 후 한 문장 설명: 예를 들어 “user labels=-100이어도 user 입력이 응답 문맥에 쓰이는 이유”.
3. 오답 확인 해설 또는 `<details>`의 정답 근거. 단순 수치값뿐 아니라 원본의 어느 줄로 설명할 수 있는지 포함한다.

이름이 등장했다는 것과 원리를 설명할 수 있다는 것을 구별해야 한다. GQA의 메모리 이점, RoPE의 위치 정보, norm과 residual의 역할도 같은 기준으로 확인하는 것이 좋다.

## 수강생 입장에서 따라갈 수 있는 부분

| 목표 | 현재 자료로 할 수 있는 것 | 추가로 필요한 지원 |
|---|---|---|
| 기본 LLM 흐름 | ID→embedding→Attention→block→LM head의 shape 추적 | B/T/D/V 정의와 확률·loss의 연결 |
| Attention | single/multi-head·causal mask를 수동 계산하고 모듈과 비교 | Q/K/V 역할의 직관, GQA 과제 shape 수정, RoPE 설명 |
| MiniMind forward | RMSNorm/FFN/residual 재현, cache 결과 일치, 실제 클래스 확인 | 함수 호출 지도와 source-reading checkpoints |
| 사전 학습 | labels shift, loss/backward/update, 저장·복원 관찰 | 기초 gradient 설명과 원본 __main__→train_epoch 연결 |
| 분류 | head-only/partial, gradient 유무·실제 값 변화 비교 | 초보자에게 Classifier subclass·동결·autograd 경계를 먼저 설명 |
| SFT | user/system mask, assistant 학습, 별도 질문 평가 비교 | JSONL→chat template→labels 경로를 원본에서 따라 읽기 |
| LoRA | BA 경로·기본 가중치 고정·저장/병합·Full FT 비교 | 원본 apply_lora의 forward 교체와 train_lora 설정 위치 안내 |
| DPO | 고정 reference·선호 쌍·token sum·margin을 코드로 관찰 | log probability·sequence 확률·sigmoid 기초 설명 |
| GRPO | 작은 숫자의 advantage·ratio·mask 연산 | 실제 rollout/온라인 RL 독립 이해는 범위 밖임을 유지 |

강점은 단순한 API 호출로 끝내지 않고 실제 MiniMind 구현과 수동 연산을 비교하는 점, head-only/partial과 Full FT/LoRA를 통제된 조건에서 비교하는 점, test 응답을 학습 질문과 분리한 점이다. 기존 SFT test 응답에는 새 질문의 오답도 남아 있어 loss와 실제 생성이 다를 수 있음을 토론할 자료가 있다. 다만 그 결과로 이해도나 일반 성능이 입증된 것은 아니다.

## 수강 후 실제로 확인할 질문

1. `[B,T]`에서 `[B,T,V]`까지 각 축을 말하고 마지막 token logits를 쓰는 이유를 설명할 수 있는가?
2. `labels=-100`인 user token도 응답 예측에 영향을 주는 이유를 설명할 수 있는가?
3. Attention에서 미래를 보게 하면 다음 token 학습에 어떤 누출이 생기는지 설명할 수 있는가?
4. 모델 내부 shift가 있는데 labels를 미리 이동하면 왜 한 token 더 밀리는가?
5. 같은 head 초기값에서 head-only와 partial의 gradient·변하는 값이 어떻게 달라지는가?
6. 실제 trainer에서 model·optimizer가 생성되는 위치와 첫 업데이트까지의 호출을 찾을 수 있는가?
7. LoRA adapter를 다른 베이스에 얹거나 config만 바꾼 checkpoint를 쓰면 무엇이 문제인가?
8. train loss 감소와 test 오답을 함께 보고 성공·한계를 구분할 수 있는가?
