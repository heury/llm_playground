# 평가에서 업데이트까지

Skill의 평가·수정 절차를 설명합니다. 네 평가자는 진단을 담당하고,
통합 담당 하나가 수정 충돌을 해소하며 패치를 적용합니다.

## 1. 조건 고정

[contract-template.json](../assets/contract-template.json)을 실행별 계약으로 복사해 채웁니다.
빈 값은 준비가 완료되었다는 뜻이 아닙니다. 완성 시 `template_only=false`로 바꿉니다.

- `target_files`: `{path, sha256}` 목록. 현재 변경 사항도 포함한 파일 상태를 기준선으로 보존합니다.
- `reference_implementations`: `{path, sha256, symbols, reason}` 목록. 외부 구현은 버전/리비전과
  확인한 출처를 함께 기록합니다. 노트북 내부 구현의 AST 해시는 result-format.md의 embedded 형식을
  사용합니다. 실제 사용하는 구현을 우선하며 projects/ 적용 여부를 명시합니다.
- `learner`, `objectives`, `prerequisites`, `required_theory`, `optional_theory`: 네 관점의 공통 범위입니다.
  사용자 정보가 없으면 README에서 추론하고 `assumptions`에 적습니다.
- `units`: `{id, section, concepts, symbols}` 목록. 이동에 취약한 행 번호만으로 식별하지 않습니다.
- `checkpoints`: 80개 항목의 `units`에 적용 단위 ID를 넣습니다. 제외는 `units=[]`와 명시적
  `excluded_reason`이 필요합니다. 핵심 항목은 `critical=true`로 지정하고 제외하지 않습니다.
  모델의 핵심 계산·정답 신호·필수 이론·실습 진행을 목표에 따라 포함하며, 핵심 목록을 비워
  핵심 확인 절차를 생략하지 않습니다. 모든 역할에 같은 핵심 개념을 전달합니다.
- `execution_scope`: 현재 요청과 환경이 허용하는 작업을 기록합니다. 템플릿은 모두 false입니다.
  업데이트 요청에 포함된 소스 수정과 가능한 저비용 검증은 담당자가 반영하며 별도 승인 단계를 만들지 않습니다.
- `required_validations`: `{id, trigger, command_or_procedure, cwd, pass_condition}` 목록입니다.
  설명·그림·셀·모델 계산 등 변경 종류별로 필요한 검증을 구체화합니다.

계약은 저장소의 `reports/<프로젝트>/<실행 ID>-contract.json`에 둡니다.
비교 실행에서는 같은 독자·목표·적용 목록·참조 구현·지표 버전을 유지합니다.
기준선 해시는 보존하고 수정본 해시를 별도로 추가합니다. 범위 변경은 새 계약 버전과 기준선이 필요합니다.

## 2. 독립 평가와 통합

각 평가자는 해당 항목을 적용 단위별로 확인하고 집계합니다.

| 단위별 상태 | 항목 최종 상태 |
| --- | --- |
| 하나라도 미충족 | 미충족, 다른 단위의 미확인도 근거에 보존 |
| 미충족 없이 미확인 존재 | 미확인 |
| 모든 적용 단위 통과 | 통과 |
| 계약상 적용 단위 없음 + 제외 이유 있음 | 해당 없음 |

일부 절의 누락을 다른 절의 좋은 설명으로 상쇄하지 않습니다. 지표는 이 집계 결과로 채점합니다.
통합자는 발견 ID별 채택/보류/기각·이유·수정 위치·완료 조건을 기록합니다.
독립 평가는 수정 전에 모두 마칩니다. 변경은 한 담당자만 수행합니다.

## 3. 수정·검증

필수 오류와 누락부터 고치고 본문·코드·그림의 대응을 유지합니다.
편집자는 현재 버전의 E5를 채점하고, 수정 이후에는 별도로 diff에 따른 의미 보존을 확인합니다.
원문 없이 편집 전후 의미가 같다고 판단하지 않습니다.

| 변경 종류 | 필요한 확인 예 |
| --- | --- |
| 설명·링크 | 개념/수식/참조 코드 대응, 상대 링크, 절 연결 |
| 그림·배치·표시 | 수정한 화면의 실제 렌더링·글자·수식·그림 대응 |
| marimo 셀 | 프로젝트 환경에서 구문·셀 의존성 검사 |
| 계산·학습 코드 | 작은 CPU 입력 순전파/필요한 역전파, 관련 회귀 검사 |

화면 열람, 작은 실행, 전체 학습을 구분합니다. 문서 수정만으로 GPU 학습을 시작하지 않습니다.
필요 검증을 실행하지 못하면 이유·영향을 남기고 검증 완료로 표시하지 않습니다.
검사 명령·작업 디렉토리는 대상 README와 현재 환경에서 확인합니다.

## 4. 재평가와 종료

새 평가 세션에 동일 계약과 수정본을 전달하여 먼저 독립 채점하고, 그 다음 이전 발견을 대조합니다.
각 발견은 해결/부분 해결/미해결로 기록하고 새 결함도 추가합니다.
전후 관측 점수·하한·확인률과 항목 상태 변화를 함께 제시합니다.

업데이트 완료 조건은 치명 오류 없음, 목표를 막는 주요 문제 해결, 핵심 미확인 없음,
필요 검증 완료입니다. 보류한 주요 문제가 남으면 변경은 제공하되 잔여 작업을 명시합니다.
점수 상승이나 85점 도달만으로 종료하지 않습니다.

산출물:

- `reports/<프로젝트>/<실행 ID>-contract.json`: 고정 계약과 버전.
- `reports/<프로젝트>/<실행 ID>-baseline-<역할>.md`: 수정 전 평가.
- `reports/<프로젝트>/<실행 ID>-after-<역할>.md`: 수정 후 평가.
- `reports/<프로젝트>/<실행 ID>-summary.md`: 발견 처리·수정 파일·검증·판정·한계.
- `outputs/<프로젝트>/<실행 ID>/`: 기준선 사본, diff, 해시, 실행 로그.

기존 MiniMind 실습의 프로젝트 경로는 `notebooks`입니다. 보고서에는 환경/패키지 버전,
모델/데이터 리비전, 실패·미실행 항목과 산출물 경로를 적습니다.
